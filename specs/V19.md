## PART 1 — Resume upload: the drop zone must stop saying "drop your resume" once there is one

This is a real bug, not just polish: after a resume is parsed the zone still reads "Drop your resume here" and still shows the upload arrow, so it looks like nothing happened.

### 1.1 States (build all four; option C is the approved visual)
Where: the `#pfDrop` label on the Profile page, and the equivalent drop target in the intro/onboarding flow (`#obDrop`), so both feel the same.

1. **Empty** (no resume): current look. Dashed 2px border, upward arrow, "Drop your resume here", "or click to choose a PDF or DOCX file". Kept, just larger per Part 2.
2. **Reading** (file chosen, parsing): dashed border becomes solid and neutral. The arrow is replaced by a **progress ring**: an SVG circle r=28, stroke-width 5, track #eceef5, progress in the brand purple, rotating -90deg to start at twelve o'clock, with the percentage in the middle (tabular numerals, 11px, 700 weight). Text under it: "Reading your resume", then a live second line naming the current step ("Experience · Education next"). Drive the ring from the real parse stages in `resume-core.js`/`resume-ui.js`, not a fake timer. If a real stage boundary isn't available, advance on real chunk progress; never animate to 90% and sit there.
3. **Done** (parsed, at least one field filled): the ring completes and turns **green** (`--ok` / #12855b), the centre becomes a filled green circle with a white tick drawn with `stroke-dashoffset` over 420ms, and below it:
   - "Resume read" (16px, 650 weight)
   - Three chips maximum, real counts only: "N roles", "N schools", "N skills". Hide any chip whose count is 0. If nothing was extracted, say "Resume saved, nothing filled in automatically" and keep the drop zone usable.
   - A text button "Replace or remove" (12.5px, brand purple, underlined). Replace opens the file picker; Remove clears the parsed data and returns to state 1. Keep the existing "Delete my resume data" behaviour and make sure both paths do the same thing.
   - The filename and size, small and muted: `Tyler_Resume_2027.pdf · 214 KB`.
4. **Error** (unreadable file, wrong type, over the size limit): red-tinted border, a warning mark instead of the ring, one plain sentence ("That file didn't open. Try a PDF or DOCX under 10 MB."), and a "Try another file" button. Never a raw parser error.

### 1.2 Behaviour and accessibility
- The old "Drop your resume here" text and arrow must be removed from the DOM in states 2–4, not just dimmed, so a screen reader doesn't announce the wrong instruction.
- `role="status"` + `aria-live="polite"` on the state line. Announce once per state change: "Reading your resume", "Resume read, 9 roles found", "Resume could not be read".
- The whole zone stays a keyboard-operable `<label>` for the file input in every state, with a visible focus ring. "Replace" and "Remove" are real buttons with 44px targets.
- `prefers-reduced-motion`: no ring spin, no tick draw; states change instantly, everything else identical.
- Drag-and-drop still works, and dragging a second file over the done state shows a light "Drop to replace" overlay that does not change the layout.
- The done state must persist across reloads if a resume was parsed (it already keeps the parsed data; make the UI read that on load instead of showing the empty zone).
- Mobile: the ring scales down to 52px, chips wrap to two rows, nothing overflows at 390px.

### 1.3 Acceptance
- Upload a real PDF, watch the ring advance through real stages, land on the tick with correct counts.
- Reload: still shows the done state, never the drop prompt.
- Remove, then upload a DOCX: works.
- Upload a broken PDF: error state, retry works.
- Screen reader announces each change once. Keyboard-only pass from empty to done to removed.

## PART 2 — Profile page: more room

Current values that make it feel tight: `.pf3-wrap` max-width 1680px with 32px side padding, `.pf-scroll` padding 24px, inputs about 44px tall, drop zone min-height 180px, column gaps 28px.

Change to:
- `.pf3-wrap` max-width **1800px**, padding `28px 48px 120px` on ≥1440px, `24px 32px` from 1024–1439px, unchanged on mobile where it already works.
- `.pf3` gap 28px (keep), and column ratio `minmax(0,.98fr) minmax(0,1.22fr) minmax(0,1fr)` (keep the middle column widest).
- `.pf-col` radius 16px, padding inside `26px 30px 34px`, panel header `26px 30px 20px`, heading 19px.
- All inputs and combobox fields **52px** tall, font-size 16px (also stops iOS zoom), label 13px 650 weight with 9px gap below.
- Vertical rhythm between fields 22px; the two-column rows 22px apart.
- Resume drop zone min-height **230px**.
- The "About you" helper text stays visible (V18 kept it) but sits 9px under the field instead of 8px, at 14px.
- Bottom save bar: 52px button, `14px 48px` padding inside, matching the new canvas width.
- Keep `.pf-scroll` internals unchanged otherwise; the columns should now fit a typical form without the inner scrollbar on 1440+ with the profile expanded. Verify on 1920, 1440, 1280, 1024, 768, 390 and both themes; no horizontal scroll anywhere.
- Do not regress Lighthouse: re-run mobile and desktop after the change and report both.

## PART 3 — Rename Autopilot to Planner

Everywhere a student sees it, "Autopilot" becomes "Planner". This includes:
- Top nav item, page heading, tab labels, and the `.ics` calendar export copy.
- Empty states, tooltips, helper text, the bell/notifications copy, and any email copy in `ops/email/`.
- The page's `<title>`, meta description, and any JSON-LD naming it.
- Docs a person might read: README, CHANGELOG entry, `docs/`, and spec references in new writing. Old specs stay as they are; don't rewrite history.

Rules:
- Do **not** rename the code: files (`autopilot.js`, `autopilot-core.js`, `ap-cal.js`), CSS classes, storage keys, hash routes (`#autopilot`), function names, or event names stay as they are. This is a label change, not a refactor, so nothing breaks for existing users' saved state.
- Keep the `#autopilot` route working and make it the Planner page. If you want a nicer URL later, add `#planner` as an alias, don't replace it.
- Capitalize "Planner" in headings and nav; lowercase "planner" mid-sentence.
- Grep and list every remaining user-visible "Autopilot" in the report so Ty can see the sweep was complete. Expected leftovers by design: internal code identifiers, old changelog entries, and old spec files.
- Watch for copy that only made sense with the old name ("Autopilot handles it for you") and rewrite it plainly ("Your planner keeps the deadlines and next steps in order").

### Acceptance
- `grep -ri autopilot` on user-visible HTML/JS text returns only internal identifiers and old changelog/spec lines. The report lists them.
- Nav, page, titles, empty state, calendar export, and emails all say Planner.
- `#autopilot` still loads the page.
