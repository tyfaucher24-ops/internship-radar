# V19.4 report: live heartbeat (no UI on the site)

## Migration review: supabase/migrations/20261104000006_live_presence.sql
I reviewed it and did not change it. Radar's own later fix (47bd790) is correct: the original declared a variable `who`, the
same name as the column, so the upsert failed with 42702 (ambiguous column).
Verdict: sound. Checked on the live database with read-only queries (Supabase connector, not service_role):
RLS enabled and forced on public.live = true/true; client grants on public.live (anon/authenticated) = 0;
heartbeat(text) executable by anon = true; admin_live() executable by anon = false.
- Upsert key `who` (primary key) means one row per person, so reloads cannot add rows for the same browser.
- admin_live(): SECURITY DEFINER, `search_path = public`, raises 42501 'not found' for non-admins; only counts leave.
- Anon callers cannot read rows (no grants, forced RLS, no select function) and can only touch their own row.
- Timestamps are timestamptz with now(); the 90 s / 5 min windows are timezone-safe.
Concerns (report only, not changed):
1. Inflation: `_caller_hash()` (migration 0003) keys anonymous callers on the FIRST x-forwarded-for value. If the
   platform passes a client-supplied X-Forwarded-For through, one script can mint fake identities and inflate `now`
   up to the 20,000-row cap, at which point real heartbeats stop being written until the daily cleanup. Erasing other
   people's rows is not possible. Fix idea for Ty: rate-limit per IP, or use the last proxy-appended XFF hop.
2. The 20,000 cap does `count(*)` on every heartbeat. Cheap at today's size; worth an estimate later.
3. `page = coalesce(excluded.page, l.page)` keeps the previous tab when a beat sends null, so `page` can be stale.
4. `search_path = public` without `pg_temp` last. Low risk: PostgREST callers cannot create temp tables.
5. People behind one shared IP (a campus network), signed out, count as one person.

## What changed on the site
- email-alerts.js: heartbeat(p_page). It beats on load (after 1.2 s, so a #privacy link reports `privacy`), on a tab
  change, when the tab becomes visible, and every 60 s while visible. At most one beat every 45 s. It sends only
  db/tracker/profile/autopilot/feedback/about/contact/privacy/terms, otherwise null. Signed out with DNT/GPC: no
  beat. A 404 stops it.
  Deviation from the brief: it has its own stop flag (`hbDead`), not the shared `dead`. Sharing it would let a missing
  0006 switch off the existing usage events as well.

- Requests per minute for a visible tab: at most one `POST /rest/v1/rpc/heartbeat` (body `{"p_page":"<tab>"|null}`).
  Hidden tabs send none.
