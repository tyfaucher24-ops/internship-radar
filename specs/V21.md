## PART 2 — Live open-internship count (public site + private stats)

### How the site says "Live" today (do not guess — verify)

- Intro (`#iN`): filled from `radar:meta` → `meta.open` ("N open internships right now").
- Find header (`#hdrCount`): `liveCounts()` over in-memory rows (fallback `META.open` /
  `META.closing_this_week`), plus a calm **"Live"** badge from `liveBadge(META.updated)` that appears
  only while the last sync is ≤ 60 minutes old (`LIVE_MAX_MIN` in `app.js`). When sync is older, the
  badge is hidden — that badge means "listings data is fresh", **not** "visitor is live".
- Ticker / Market has its own "Live updates paused" stale-dot when refreshes stop.

### What to build

**A. Public, always-current open count on Intern Index**

Show a public count of open internships that is never hardcoded and updates every sync, e.g. in the
Find header / hero area as:

`{N} open internships · Live`

Rules:

1. `N` comes from the same definition of open the site already uses (`markLive` / `pipeline/hygiene.is_open`
   / `meta.open` — status open, not hidden, not past term, deadline today or later, plus user-added).
2. Prefer computing `N` from the listings the page already loads (`liveCounts().open`). Also keep
   `meta.open` (and/or a tiny `data/counts.json` written each sync) in lockstep so the intro counter
   and any pre-listings paint match. Never a literal number in HTML/JS/CSS.
3. The word **Live** next to the open count means "this number came from the latest sync / current
   dataset", not the visitor-heartbeat. Keep the existing 60-minute freshness badge behaviour for the
   sync-freshness signal (or fold it into the same line honestly — if you merge them, document the
   exact copy in the report and keep accessibility: `aria-label` must say what Live means).
4. After every successful sync publish, `meta.open` (and `counts.json` if added) equals the open count
   the next page load will show. Partial syncs must not invent a drop: keep the existing gate.

**B. Private stats site — listing health numbers**

Add to https://tyfaucher24-ops.github.io/intern-index-stats/ (separate PR in that repo is fine; specify
the contract here):

- open listings (same `N`)
- new-today (became open / first_seen today, America/New_York day boundary)
- closed-today (moved to closed today)
- per-source counts (by `source_type` and/or `source` / adapter — pick one breakdown and stick to it;
  include at least adapter/ATS and lead-list vs employer-board)

**Pick the simplest secure option (required choice for this build):**

**Public JSON written each sync** — extend `data/meta.json` (or add `data/counts.json` next to it) with:

```json
{
  "updated": "<iso from sync>",
  "open": <int>,
  "new_today": <int>,
  "closed_today": <int>,
  "by_source": { "<source_key>": <int>, "...": 0 }
}
```

These numbers are already public on the product site, so they do not need admin-only RLS. The stats
site fetches the published file from the live Intern Index origin (cache-bust with `?ts=`).

Do **not** put a service_role key in the sync workflow. If a later revision wants a Supabase table
instead, it needs a migration applied via Supabase (`apply_migration` / SQL editor), admin-only RLS,
and a write path that does not embed service_role in the client — out of scope unless the public JSON
path is somehow blocked.

No new Supabase migration is required for Part 2 under the public-JSON choice. If the builder instead
chooses a Supabase table/RPC, they must: (1) write the migration under `supabase/migrations/`,
(2) apply it via Supabase (connector `apply_migration` or paste in SQL editor), (3) document the
apply step in `ops/V21_REPORT.md`, (4) keep RLS so only admins can `select`.

### Acceptance

- Grep the built JS/HTML: no hardcoded open-count integer that pretends to be current inventory.
- After a sync that changes open by a known Δ (measure in audit, or a fixture sync in tests), reload
  Find and intro: both show the new `N` within one refresh cycle.
- Copy on Find matches the form `{N} open internships · Live` (or the documented merge with the

- Stats site (signed in as admin) shows open / new-today / closed-today / per-source matching the

## PART 5 — Role descriptions + company about

### Today

- Sync already stores description text in `data/desc/{shard}.json` and sets `has_desc` when present
  (`pipeline/sync.py`). Drawer loads via `descOf(x)`.
- When missing, detail shows: "Full description is on the company posting."
- There is a `#dAbout` blurb slot filled from `roleBlurb` only when a description exists — not a
  durable per-company about cache.
- Wikidata/Commons are already allow-listed in `pipeline/logos.py` delays — reuse that net stack for
  short descriptions if used.

### What to build

**A. Role description**

1. Pull the full role description from the source whenever the adapter exposes it (Greenhouse
   `content=true`, Lever/Ashby/SmartRecruiters/Workable/Recruitee/BambooHR/Workday detail,
   JSON-LD `description`, feed APIs that include description, etc.).
2. Sanitize HTML → safe plain text / simple paragraphs (no scripts, no inline event handlers, no
   remote HTML execution). Existing escaping in the drawer (`esc`) stays; prefer storing plain text
   in `data/desc/` as today.
3. Show the description in the detail panel (summary + full posting), same layout chrome — no redesign.

**B. Company about**

1. For every company with ≥1 listing, cache a short **About \<Company\>** blurb (≈1–3 sentences) in a
   per-company store (e.g. `data/company_about/{shard}.json` or a field in a companies sidecar —
   pick one and document it). Refresh on a slow cadence (e.g. when missing or older than 30 days).
2. Allowed free sources only, in preference order:
   1. Employer’s own ATS board intro / department blurb if the public JSON includes it
   2. Careers page meta description (robots-allowed page only)
   3. Wikipedia / Wikidata short description with visible attribution ("Source: Wikidata" / Wikipedia)
3. Never pay for data. Never use login-walled text.

**C. Fallback when the role has no description**

Detail panel description area must not be empty. Show:

- muted line: **`The employer didn't post a full description. Here's a bit about the company.`**
- the About blurb
- the apply / view-posting link (existing button)

If both role desc and company about are missing, show that muted line plus a one-line honest fallback
("See the company posting for details.") and the apply link — still **not** an empty area.

### Acceptance

- **0 detail panels with an empty description area** (open a random sample of ≥ 30 open listings
  including ones with `has_desc=false`; automated test that the drawer HTML for missing desc contains
  the fallback sentence or a non-empty about block).
- Measure before/after in `ops/V21_REPORT.md`:
  - open listings with `has_desc=true`
  - companies with a cached about blurb
  - open listings whose detail would have hit the empty fallback before vs after
- Sanitizer unit tests: script tags stripped; plain text round-trip.
- Attribution present when the blurb came from Wikidata/Wikipedia.
- Card titles still 2-line clamped; detail layout otherwise unchanged.
- axe 0 on a detail panel with full desc and one with the company-about fallback.
